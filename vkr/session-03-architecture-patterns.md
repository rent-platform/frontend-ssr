# Сессия 3 — Архитектурные решения и паттерны проектирования

---

## 4. Архитектурные решения и паттерны проектирования клиентской части

Проектирование клиентской части веб-приложения платформы аренды вещей «Арендай» основывалось на совокупности архитектурных решений и паттернов, направленных на достижение масштабируемости, сопровождаемости, тестируемости и визуальной согласованности пользовательского интерфейса. Каждое из принятых решений обусловлено спецификой предметной области — многоролевой платформы с развитым жизненным циклом сделки, модерацией контента и интеграцией с платёжной системой — и продиктовано необходимостью поддержки параллельной разработки в команде из двух специалистов с разграниченными зонами ответственности. Ниже приведено подробное описание каждого из применённых подходов.

---

### 4.1. Модульная архитектура на основе функциональной декомпозиции

В качестве базового архитектурного подхода к организации исходного кода клиентской части применена модульная архитектура, построенная по принципу функциональной декомпозиции. Данный подход предполагает разбиение всего пользовательского интерфейса на изолированные функциональные модули, каждый из которых инкапсулирует полный набор артефактов, необходимых для реализации конкретной области функциональности: компоненты представления, пользовательские перехватчики состояния, описания типов данных, вспомогательные функции, файлы стилей, имитационные данные и модульные тесты.

В проекте реализовано 15 функциональных модулей, размещённых в специализированном каталоге слоя представления. Каждый модуль представляет собой автономную единицу, которая может разрабатываться, тестироваться и модифицироваться независимо от остальных модулей. Экспорт публичного программного интерфейса каждого модуля осуществляется через единственный индексный файл, что обеспечивает чёткую границу между внутренней реализацией и внешним контрактом.

Преимущества данного подхода в контексте разрабатываемой платформы:

1. Масштабируемость — добавление нового функционала (например, модуля логистики или модуля страхования) сводится к созданию нового функционального модуля без модификации существующих.
2. Изолированность — изменение внутренней реализации модуля каталога не затрагивает модуль чата или модуль оплаты, поскольку каждый модуль экспортирует лишь строго определённый набор компонентов и типов.
3. Параллельная разработка — разработчик пользовательского интерфейса и разработчик бизнес-слоя работают в разных каталогах исходного кода без конфликтов системы контроля версий.
4. Навигируемость — при объёме в 394 файла и приблизительно 64 500 строк кода предсказуемая структура каталогов существенно сокращает время поиска нужного артефакта.

Общая иерархия зависимостей слоёв построена по принципу восходящей абстракции и выглядит следующим образом. Нижний уровень — дизайн-токены и глобальные стили — представляет фундамент визуального оформления. На нём располагается уровень из 17 разделяемых компонентов интерфейса, используемых во всех модулях. Далее следует уровень из 15 функциональных модулей, каждый из которых реализует самостоятельную область функциональности. Верхний уровень — 17 страничных маршрутов приложения — объединяет модули в единое целое. При этом функциональные модули импортируют типы сущностей и пользовательские перехватчики из каталога бизнес-слоя, принадлежащего зоне ответственности другого разработчика. Данная зависимость является строго односторонней: слой представления потребляет контракты бизнес-слоя, но не экспортирует в него ничего, что соответствует принципу инверсии зависимостей.

### 4.2. Компонентно-ориентированная разработка

Пользовательский интерфейс платформы построен на основе компонентно-ориентированного подхода, при котором каждый визуальный элемент представляет собой изолированный, переиспользуемый компонент с определённым набором входных свойств, внутренним состоянием и жизненным циклом. Компонентная модель обеспечивает декларативное описание интерфейса: разработчик определяет, как должен выглядеть экран в зависимости от текущего состояния данных, а библиотека отрисовки самостоятельно вычисляет минимально необходимые обновления документа.

В проекте выделены два уровня компонентов:

**Разделяемые компоненты** (17 единиц) — универсальные элементы интерфейса, используемые в нескольких функциональных модулях. К ним относятся: универсальное текстовое поле ввода с маской телефонного номера и плавающими подписями полей; формы авторизации и регистрации; компонент вкладок с поддержкой обобщённых типов, иконок и числовых индикаторов; компонент перехвата ошибок отрисовки; индикатор загрузки с мерцающей анимацией; компонент пустого состояния; кнопка прокрутки к началу страницы; модальное окно «Поделиться»; компонент постраничной навигации; выпадающий список для административных панелей; заголовок таблицы с переключением сортировки; скелетон табличного представления; переключатель визуальной темы (светлая и тёмная); система всплывающих уведомлений; ссылка возврата на предыдущую страницу и ссылка для перехода к основному содержимому, минуя навигационное меню.

**Локальные компоненты** (подкаталоги внутри каждого функционального модуля) — компоненты, специфичные для конкретного модуля и не предназначенные для переиспользования за его пределами. Например, модуль каталога содержит 38 локальных компонентов, распределённых по четырём подгруппам: карточки товаров, детальная страница товара, элементы фильтрации и поиска, а также компоненты-обёртки макета. Модуль панели администратора содержит 10 локальных компонентов, включая детальные карточки объявлений и пользователей, галерею изображений и миниатюрную столбчатую диаграмму.

Такое разделение обеспечивает баланс между переиспользованием и инкапсуляцией: общие визуальные паттерны вынесены на уровень разделяемых компонентов, тогда как специфичная для конкретного сценария логика отображения остаётся внутри соответствующего функционального модуля.

---

### 4.3. Централизованный реэкспорт через индексные файлы

Во всех модулях, каталогах компонентов, утилит, перехватчиков состояния, типов и контекстов применён паттерн централизованного реэкспорта посредством индексных файлов. Каждый такой файл объединяет и переэкспортирует публичный программный интерфейс модуля, скрывая внутреннюю структуру каталогов от потребителей. Благодаря этому потребитель импортирует артефакты по сокращённому пути, а внутренняя реструктуризация модуля (переименование файлов, перемещение компонентов между подкаталогами) не приводит к каскадному изменению импортов во всём проекте. На уровне функциональных модулей единый индексный файл реэкспортирует корневые компоненты всех 15 модулей, выступая единой точкой доступа для страничных маршрутов.

---

### 4.4. Модульная изоляция стилей

Стилизация компонентов выполнена с применением технологии модульных каскадных таблиц стилей в сочетании с препроцессором. Каждый компонент или функциональный модуль имеет собственный файл стилей, при компиляции которого генерируются уникальные имена классов с автоматическими суффиксами, гарантирующими полное отсутствие глобальных конфликтов имён. В проекте насчитывается 132 файла стилей.

Данный подход решает типичную проблему крупных веб-приложений — непредсказуемость каскадирования при наличии сотен компонентов. Стили модуля каталога (8 частичных файлов общим объёмом свыше 77 000 байт) физически не могут повлиять на стили модуля оплаты (2 файла), поскольку каждый из них генерирует уникальные идентификаторы классов.

Внутри функциональных модулей крупные файлы стилей разбиты на частичные файлы по принципу единственной ответственности: базовые стили, стили сетки и карточек, стили адаптивности, стили отдельных секций и состояний. Для динамической композиции классов в зависимости от состояния компонента (активная вкладка, тёмная тема, текущий статус сделки) применяется специализированная утилита условного объединения имён классов.

---

### 4.5. Централизованная система дизайн-токенов

Визуальная согласованность всех 17 страничных маршрутов приложения обеспечивается централизованной системой дизайн-токенов. Дизайн-токены представляют собой именованные переменные, определённые в едином файле конфигурации стилей и задающие значения для следующих категорий визуальных параметров: цветовая палитра (основные, акцентные, фоновые цвета для светлой и тёмной темы), типографика (семейство шрифтов, размеры, межстрочные интервалы, насыщенность), сетка отступов (от минимального до максимального с шагом), тени (от лёгкой до объёмной), радиусы скругления углов, градиенты (поверхности, акценты, стекломорфизм), уровни наложения элементов и контрольные точки адаптивности для различных типов устройств.

Все компоненты проекта обращаются к токенам через единую директиву подключения, что гарантирует единообразие визуального оформления и позволяет изменять параметры дизайн-системы в одном месте с мгновенным распространением изменений на весь проект.

---

### 4.6. Библиотека переиспользуемых примесей стилей

Помимо дизайн-токенов, дизайн-система включает библиотеку из более чем 20 примесей (многократно используемых фрагментов стилевых правил), размещённых в специализированном файле. Примеси инкапсулируют повторяющиеся визуальные паттерны и обеспечивают единообразие их применения во всех модулях:

- адаптивные точки перелома — обеспечивают единообразное применение медиа-запросов во всех 12 файлах адаптивных стилей;
- центрирование на основе гибкой раскладки — используется в десятках компонентов для вертикального и горизонтального выравнивания;
- карточка с эффектом стекломорфизма — применяется в модулях гостевой страницы, деталей сделки и каталога для создания эффекта полупрозрачного стекла с размытием фона;
- анимация мерцающего индикатора загрузки — используется всеми скелетонными экранами;
- кольцо фокуса — обеспечивает визуальную обратную связь при клавиатурной навигации по интерактивным элементам;
- усечение текста — ограничивает длину текстовых элементов с добавлением многоточия.

---

### 4.7. Адаптивный дизайн

Адаптивность интерфейса реализована через 12 файлов адаптивных стилей, размещённых в каталогах стилей соответствующих функциональных модулей. Каждый файл определяет медиа-запросы с использованием примесей из централизованной библиотеки, что обеспечивает корректное отображение на устройствах с различными размерами экрана: настольных компьютерах, планшетах и мобильных телефонах. Контрольные точки перелома определены централизованно в файле дизайн-токенов и единообразно используются во всех модулях.

---

### 4.8. Разделение слоя представления и бизнес-логики

Архитектура проекта реализует чёткое разделение между слоем представления и бизнес-слоем. Слой представления (зона ответственности автора настоящей работы) отвечает исключительно за визуальное оформление, компоновку элементов, анимации, навигацию, обработку пользовательских событий и валидацию форм на стороне клиента. Вся бизнес-логика — взаимодействие с серверным программным интерфейсом, управление глобальным состоянием приложения, преобразование данных из серверного формата в клиентский — сосредоточена в бизнес-слое, принадлежащем зоне ответственности второго разработчика.

Связь между слоями осуществляется через два механизма. Первый — импорт типов сущностей, представляющих точное отображение схемы базы данных, что обеспечивает типобезопасность данных на уровне компиляции. Второй — импорт пользовательских перехватчиков состояния для выполнения операций с серверным программным интерфейсом (загрузка данных, создание и обновление записей). Слой представления никогда не обращается к серверному программному интерфейсу напрямую, что обеспечивает возможность замены реализации серверного взаимодействия без модификации компонентов интерфейса.

---

### 4.9. Разработка на основе имитационных данных

Каждый из 15 функциональных модулей содержит файл имитационных данных, предоставляющий реалистичные наборы объектов для автономной разработки и демонстрации. Данный подход позволяет разрабатывать и тестировать пользовательский интерфейс без зависимости от готовности серверной части: разработчик интерфейса создаёт, стилизует и верифицирует визуальное поведение компонентов, используя имитационные данные, а при подключении реального серверного программного интерфейса заменяет источник данных без изменения компонентов представления.

Перехватчики состояния, работающие с имитационными данными (9 перехватчиков в модуле панели администратора, 4 перехватчика в модуле панели модератора), используют отложенное выполнение с задержкой приблизительно 600 миллисекунд для имитации сетевой задержки. Это позволяет верифицировать корректность отображения состояний загрузки, скелетонных экранов и переходов между состояниями в условиях, приближённых к реальным.

---

### 4.10. Перехват ошибок отрисовки

Для обеспечения отказоустойчивости пользовательского интерфейса реализован специализированный компонент перехвата ошибок отрисовки, построенный на основе классового компонента с методом жизненного цикла перехвата исключений. Компонент размещается в иерархии компонентов в качестве обёртки и перехватывает все исключения, возникающие при отрисовке дочерних элементов. Вместо аварийного прекращения работы всего приложения (отображения пустого белого экрана) компонент показывает заменяющее содержимое: пользовательский элемент, переданный через свойство, либо стандартное сообщение об ошибке с кнопкой повторной попытки.

Данный компонент покрыт пятью модульными тестами, проверяющими корректность отрисовки дочерних элементов в штатном режиме, отображение пользовательского заменяющего элемента, вызов функции обратного вызова и отображение стандартного интерфейса ошибки.

---

### 4.11. Индикация загрузки посредством скелетонных экранов

Вместо традиционных индикаторов вращения в проекте применены скелетонные экраны — макеты страниц, повторяющие структуру реального содержимого, но заполненные анимированными блоками-заглушками с мерцающей анимацией. Данный подход снижает воспринимаемое время ожидания, поскольку пользователь видит предварительную структуру страницы ещё до загрузки данных, что создаёт ощущение постепенного заполнения контентом.

Скелетонные экраны реализованы в шести функциональных модулях: каталог (скелетон карточки товара), личный кабинет (скелетон панели управления), панель администратора (скелетон таблиц и карточек), панель модератора (скелетон табличного представления), оплата (скелетон страницы оплаты) и публичный профиль. Мерцающая анимация инкапсулирована в разделяемом компоненте и в примеси стилей, что обеспечивает визуальную согласованность индикации загрузки во всех модулях.

---

### 4.12. Бесконечная прокрутка

Для загрузки больших наборов данных (каталог объявлений, списки отзывов) реализован пользовательский перехватчик состояния бесконечной прокрутки, использующий программный интерфейс наблюдателя пересечений. Перехватчик отслеживает видимость специального элемента-наблюдателя, размещённого в конце отображаемого списка. При попадании данного элемента в область видимости окна просмотра автоматически вызывается функция загрузки следующей порции данных. Подход исключает необходимость ручного перехода между страницами списка и обеспечивает плавный, непрерывный пользовательский опыт при просмотре каталога объявлений.

---

### 4.13. Клавиатурная навигация и обеспечение доступности

Доступность интерфейса для пользователей с ограниченными возможностями обеспечивается несколькими взаимодополняющими механизмами:

- Компонент перехода к основному содержимому — реализует скрытую ссылку, появляющуюся при первом нажатии клавиши табуляции и позволяющую перейти к основной области содержимого, минуя навигационное меню. Данный паттерн рекомендован руководством по обеспечению доступности веб-содержимого.

- Компонент вкладок — использует атрибуты доступности для обозначения выбранной вкладки и управления порядком фокусировки, что обеспечивает навигацию клавиатурой между вкладками без использования мыши.

- Перехватчик ловушки фокуса — реализует циклическое перемещение фокуса внутри модального окна: при нажатии клавиши табуляции на последнем интерактивном элементе фокус перемещается на первый, а при нажатии обратной клавиши табуляции на первом элементе — на последний. Это предотвращает «утечку» фокуса за пределы модального окна.

- Глобальные стили содержат правила визуального выделения элементов при фокусировке клавиатурой — кольцо фокуса с акцентным цветом и отступом, обеспечивающее визуальную обратную связь.

## 6.16. Паттерн организации функциональных модулей

Каждый из 15 функциональных модулей, размещённых в каталоге слоя представления, следует единой внутренней структуре, обеспечивающей предсказуемость навигации по исходному коду и единообразие архитектурных решений во всём проекте. Описание типовой структуры функционального модуля приведено ниже.

**Корневой компонент** — главный компонент модуля, представляющий точку входа и определяющий общую компоновку страницы или экрана. Все корневые компоненты объявлены с директивой клиентской отрисовки, что обеспечивает возможность использования перехватчиков состояния, эффектов жизненного цикла и обработчиков событий. Корневой компонент импортирует вложенные компоненты, перехватчики, типы, стили и имитационные данные из текущего модуля, а также разделяемые компоненты и утилиты из соответствующих каталогов общего уровня.

**Корневой файл стилей** — файл модульных каскадных таблиц стилей, соответствующий корневому компоненту. В крупных модулях данный файл содержит директивы подключения частичных файлов стилей из подкаталога стилей.

**Каталог вложенных компонентов** — содержит компоненты, специфичные для данного функционального модуля и не предназначенные для использования за его пределами. В крупных модулях компоненты дополнительно группируются по функциональному назначению в подкаталоги. Например, в модуле каталога выделены четыре подгруппы: карточки товаров, детальная страница товара, элементы фильтрации и поиска, а также компоненты-обёртки макета.

**Каталог пользовательских перехватчиков состояния** — содержит перехватчики, инкапсулирующие логику управления состоянием, фильтрацией, сортировкой и взаимодействием с данными. Перехватчики модулей панели администратора и панели модератора дополнительно включают реэкспорты общих перехватчиков постраничной навигации и сортировки из каталога общих перехватчиков.

**Каталог стилей** — содержит частичные файлы стилей, разделённые по функциональному назначению: базовые стили, стили сетки, стили адаптивности, стили отдельных секций и состояний. Каждый частичный файл именуется с префиксом подчёркивания, что является стандартной конвенцией препроцессора и обозначает файл, не предназначенный для самостоятельной компиляции.

**Файл описания типов** — определяет интерфейсы, типы-объединения и псевдонимы типов, специфичные для данного модуля. Импортирует базовые типы сущностей из бизнес-слоя и типы представления из каталога общих типов слоя представления.

**Файл имитационных данных** — экспортирует массивы и объекты с реалистичными данными для автономной разработки и демонстрации. Имитационные данные воспроизводят структуру реальных ответов серверного программного интерфейса и содержат данные на русском языке, что позволяет проводить полноценное визуальное тестирование интерфейса без подключения к серверу.

**Файл вспомогательных функций** — содержит чистые функции преобразования данных, форматирования, маппинга статусов и иных операций, не связанных с управлением состоянием. Присутствует в модулях, требующих нетривиальной логики: каталог (функции применения фильтров, сортировки, сериализации), личный кабинет (преобразование объявлений, вычисление заполненности профиля), публичный профиль (метки доверия), детали сделки (пошаговый индикатор, определение доступных действий по статусу и роли), оплата (маппинг статусов платежа в состояния интерфейса), панель администратора (справочники статусов и ролей).

**Каталог тестов** — содержит модульные тесты для вспомогательных функций и функций преобразования данных. Присутствует в модулях каталога (51 тест), личного кабинета (20 тестов) и публичного профиля (13 тестов).

**Индексный файл** — реэкспортирует публичный программный интерфейс модуля: корневые компоненты, типы и вспомогательные функции, необходимые внешним потребителям.

Типовая структура каталога функционального модуля:

```
Модуль/
├── Корневой компонент       — точка входа модуля
├── Файл стилей модуля       — модульные стили корневого компонента
├── компоненты/              — вложенные компоненты (только для этого модуля)
├── перехватчики/            — пользовательские перехватчики состояния
├── стили/                   — частичные файлы стилей
├── типы                     — описание типов данных модуля
├── имитационные данные      — реалистичные наборы данных
├── вспомогательные функции  — чистые функции преобразования
├── тесты/                   — модульные тесты (при наличии)
└── индексный файл           — централизованный реэкспорт
```

Не все элементы структуры обязательны: минимальный модуль (модуль информационных страниц, 9 файлов) содержит только корневой компонент, файл стилей, каталог стилей и индексный файл. Максимально развёрнутый модуль (модуль каталога, 58 файлов) включает все перечисленные элементы, при этом каталог компонентов содержит четыре уровня вложенности с собственными файлами стилей.

Второй (6 254 байт) реализует страницу результатов поиска с расширенной панелью фильтров, активными метками применённых фильтров и переключателем сортировки.

Подгруппа содержит девять файлов стилей.

- Подгруппа макета (2 файла) содержит компоненты-обёртки: шапку каталога с навигацией, логотипом и иконками и подвал каталога с контактной информацией.

### 6.15.2. Модуль панели администратора (32 файла)

Модуль панели модератора реализует интерфейс модерации контента платформы. Модуль обеспечивает покрытие 8 сценариев модератора: проверка объявлений на соответствие правилам, подтверждение публикации, отклонение объявлений с указанием причины, блокировка некорректного контента, просмотр и обработка жалоб пользователей, уведомление участников о решении по жалобе, просмотр истории действий и контроль нарушений правил платформы.

**Корневой компонент** (1 329 байт) реализует переключение между четырьмя вкладками с анимацией: очередь модерации, жалобы, модерация отзывов и журнал действий. Структурно идентичен корневому компоненту панели администратора, что обеспечивает архитектурную согласованность и предсказуемость для разработчиков.

**Компоненты** (8 файлов):

- Вкладка очереди модерации (13 772 байт) — список объявлений, ожидающих проверки, с детальным просмотром содержимого (заголовок, описание, фотографии, категория, цена, залог, город, место передачи), кнопками одобрения и отклонения с указанием причины, индикацией процесса обработки. Одобренные объявления переводятся в статус «Активно», отклонённые — в статус «Отклонено» с сохранением причины.
- Вкладка жалоб (15 451 байт) — управление жалобами пользователей с хронологией обработки, фильтрацией по четырём статусам (открыта, в обработке, решена, отклонена), детальным просмотром содержания жалобы, историей комментариев и кнопками изменения статуса.
- Вкладка модерации отзывов (11 715 байт) — список отзывов с возможностью удаления нарушающих правила платформы и снятия пометки с отзывов, ошибочно отмеченных пользователями как неуместные.
- Вкладка журнала действий (6 153 байт) — хронологический журнал действий модератора с фильтрацией по 6 типам действий (одобрение объявления, отклонение объявления, решение по жалобе, отклонение жалобы, удаление отзыва, снятие пометки с отзыва), текстовым поиском, сортировкой по столбцам и диапазоном дат.
- Четыре файла реэкспорта разделяемых компонентов: выпадающий список, постраничная навигация, заголовок таблицы с сортировкой, скелетон таблицы.

Важной архитектурной особенностью является направление зависимости между модулями модератора и администратора: модуль администратора импортирует перехватчик обработки жалоб из модуля модератора, тогда как модуль модератора не зависит от модуля администратора. Оба модуля импортируют общие перехватчики постраничной навигации и сортировки из каталога общих перехватчиков, избегая перекрёстных зависимостей. Данная архитектура обеспечивает однонаправленность графа зависимостей и упрощает сопровождение кода.

**Файл описания типов** (3 427 байт) определяет тип вкладки модератора из 4 значений, тип действия модератора из 6 значений, интерфейсы элемента очереди модерации, жалобы, комментария к жалобе, модерируемого отзыва, записи журнала действий и фильтра журнала.
